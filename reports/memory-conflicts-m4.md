# M4: Модель конфликтов памяти — отчёт об этапе

Дата: 26.11.2026 · База: v0.14.0-orcarouter + M4 · Коммиты: m4-migration → m4-downgrade → m4-context → m4-engines → m4-api-ui → m4-tests-docs

## Что было (аудит P1.2)

Разрешение конфликтов было грубым: в `Pipeline.chat` стояла проверка «если среди найденных заметок есть исправленная (`revision > 1`) — удалить из запроса **все** ответы Кумара». Одна правка любой заметки стирала весь диалоговый контекст персонажа со зрителем. Статусов факта не существовало, temporal validity отсутствовала, история изменений была видна только в служебной таблице `note_versions`. При росте памяти это гарантированно деградировало личность.

## Что стало

**Жизненный цикл факта** — явный, в SQLite:

| Статус | Кто ставит | Что означает |
|---|---|---|
| `active` | система | актуальный факт, попадает в поиск и дефолтный список |
| `superseded` | система (правка текста/ключа) | заменён новой версией; ссылка `superseded_by_id` ведёт на актуальную |
| `disputed` | только оператор | спорная пометка; историю **не** инвалидирует |
| `retracted` | оператор | отозван; исчезает из поиска и памяти, тело и история сохраняются |

Новые поля `notes`: `status` (CHECK-enum), `valid_from`, `valid_to`, `superseded_by_id` (старая → новая: вопрос «что сейчас верно?» — один запрос, решение согласовано в плане).

**Суперсессия вместо правки на месте.** Изменение текста или ключа создаёт новую строку (`active`, сквозной номер ревизии) и помечает старую; ничего не удаляется. Правка только метаданных остаётся правкой на месте (согласовано). Устаревшая строка отказывается редактироваться и подсказывает актуальный номер.

**Точечная инвалидация истории.** Устаревшие факты находятся двумя детерминированными путями без эмбеддингов (M2/M3 не тронуты): предки найденных active-заметок по цепочкам суперсессий + лексический отбор отозванных/заменённых по основам слов (связь = основа ключа или ≥2 общие основы тела; консервативно против ложных удалений). Из истории исключаются **только** ответы Кумара, связанные с устаревшим фактом, — с пометкой причины; посторонние остаются. Параллельно модель получает `<conflicting_facts>` отдельным system-сообщением до `<reference_data>`: «Ранее было сказано X, но это неактуально. Актуально: Y». Характер (`config/character.md`, контракт C1) не смешивается с коррекцией памяти.

**Миграция** — идемпотентная, одна транзакция `BEGIN IMMEDIATE` (по уточнению: индекс пересоздаётся после бэкфилла `valid_from=created` и схлопывания дублей, до любых пользовательских вставок). Дубли ключей из баз до уникального индекса не удаляются молча: новейшая остаётся `active`, старые помечаются `superseded` со ссылкой, отчёт пишется в `state('m4_migration_report')`. Граничный случай проверен тестом: 1230 заметок, 30 дубликатов → 1201 активная + 29 устаревших, ноль потерь.

**Downgrade** — `tools/downgrade_m4.py` (безопаснее upgrade, как заказано): пре-проверки останавливают скрипт со списком проблемных ID при битых `superseded_by_id` и нарушениях FK; автоматический срез-бэкап; тела дубликатов архивируются в `note_versions` до удаления строк; 12-шаговый rebuild к схеме Этапа 0; `foreign_key_check` + `integrity_check`; без `--yes` — только план; повторный запуск — честный no-op.

**API/UI.** `GET /api/notes?include_history=true`; `GET /api/notes/{id}/versions` — история цепочки от любой точки; `PUT` возвращает `mode/old_id/new_id`; `DELETE` — отзвание, `?hard=true` — физическое удаление для PII (согласовано); `POST /api/notes/{id}/status` — кураторские пометки. Панель: цветные бейджи статусов (активна/оспорена/заменена/отозвана), указатель актуальной версии, «Просмотреть историю версий» по цепочке, «Пометить спорной», «Отозвать», «Удалить навсегда» с явными подтверждениями, переключатель показа истории. Все изменяющие эндпоинты по-прежнему под `admin_guard`.

## Совместимость с Этапом 0

- admin token: все новые изменяющие эндпоинты защищены (тест);
- prompt contract: character.md по-прежнему единственный источник личности; блок конфликтов — аддитивное system-сообщение (тест на разделение);
- safe_float: не изменён; нулевые значения продолжают сохраняться как нули (старые тесты зелёные);
- FTS5 (M2) и semantic search (M3): не затронуты — инвалидация детерминированная, на основах слов.

## Тесты

121 тест (было 102): +19 в `tests/test_conflicts.py` — цепочка, правка метаданных, отказ править устаревшую строку, отзвание/жёсткое удаление, точечная инвалидация с сохранением посторонних ответов, disputed-поведение, приватность отозванного, разделение блока в движке, миграции (малая/дубликаты/1000+/идемпотентность), downgrade (успех/битые ссылки/re-open), API (дефолт-фильтр, цепочки, статусы, hard delete, admin guard).

## Ограничения и что дальше

- Связь «ответ Кумара ↔ факт» лексическая и намеренно консервативная: редкие случаи связи «в одном слове» не инвалидируются автоматически — их ловит `<conflicting_facts>` (модель всё равно видит, что факт устарел). Автоматическая семантическая близость — предмет M3/M5.
- `disputed` пока не влияет на ранжирование контекста, кроме видимости с бейджем — ручной инструмент, как согласовано.
- Отзват физически не удаляет векторы до перестройки индекса — стандартное поведение сборки (как и раньше для удалённых сообщений).
